## v1.1: snapshot, fork, rollback, and operator tools

Status: design + implementation plan
Date: 2026-05-19
Owner: Vlad (state ops) + Marius (operator tools)
Related: `docs/plans/2026-05-14-local-agentic-dev-env-design.md` (v1, shipped May 18)
Target ship: 2026-06-09 (SF developer-validation cohort)

## Goal

Turn Opnble into a local sandbox runtime that a host-side agent (Cursor, Claude Code) can drive against a real project: read and write files, exec shell commands in the project environment, snapshot the working tree at a point in time, fork a sandbox to explore an alternative, and roll back if the experiment fails.

The audience is 10 to 15 SF developers between Jun 9 and Jul 7. The success criterion is "they spent a real workday in this loop on their own codebase," not "they were impressed by a demo." Install in under 60 seconds on a stranger's MacBook. Robustness beats theater.

### Six new MCP tools

| Group | Tool | Returns |
|---|---|---|
| Operator | `exec_command({ slug, cmd, cwd?, env?, timeout_ms? })` | `{ stdout, stderr, exit_code, truncated }` |
| Operator | `read_file({ slug, path, max_bytes? })` | `{ content, encoding, size, truncated }` |
| Operator | `write_file({ slug, path, content, mode? })` | `{ bytes_written }` |
| State | `snapshot_project({ slug, label? })` | `{ snapshot_id, label, taken_at }` |
| State | `fork_project({ slug, count?, label? })` | `[{ slug, parent_slug, status, port?, url? }]` |
| State | `rollback_project({ slug, snapshot_id })` | `{ snapshot_id, restored_at }` |

### Non-goals for v1.1

- No agent runtime inside Opnble. Agents remain on the host in Cursor or Claude Code.
- No editor integration beyond what v1 already writes (`.cursor/mcp.json`).
- No new platform releases. macOS ARM (vfkit) is the demo target. WSL2, QEMU, and Podman host paths stay buildable but unreleased.
- No new runtimes (Python, Go, Postgres-as-data). v1.1 is honest about being a Node, React, Next workflow.
- No external deploy targets beyond GitHub Pages (deferred to v1.2).

## Background facts (verified against current code)

- Project source trees live on the host at `~/.opnble/repos/<project-id>/` and are exposed to the VM through a single virtio-fs share. `vm/vfkit.rs:200` mounts `repos_dir()` with one `mountTag`; new project directories appear inside the VM automatically with no remount required. This is the architectural fact that makes the snapshot story simple.
- `vm/clone.rs:76-97` already wraps `clonefile(2)` for the VM disk image. Apple's `clonefile(3)` syscall accepts directories with `CLONE_NOFOLLOW` and recurses internally in one call. We extend the same module to clone project trees.
- `agent/src/service.rs:507` exposes `ExecHost` for running arbitrary shell on the Alpine VM host. `podman exec <name> sh -c <cmd>` from the VM host enters the project container without a proto change.
- `agent/src/service.rs:124-148` already implements `canonicalize_existing_within_repos` and `canonicalize_parent_within_repos` against the VM's view of `repos/`. The host-side equivalent is one helper away.
- `projects/store.rs:202-238`: `allocate_port` is monotonic over `next_port`. N concurrent siblings allocate N sequential ports cleanly. We do NOT need to extend it.
- `projects/types.rs:227-255`: `Project` already has `#[serde(default)]` for newer fields. Adding `parent_project_id: Option<ProjectId>` and `forked_at: Option<u64>` preserves backward-compat with old `state.json`.
- `projects/orchestrator.rs:108`: `force_stop_and_remove` already exists and is reused by restart. Rollback uses the same primitive.
- `mcp/server.rs:`-`McpDeps` already plumbs `Arc`s for `ProjectStore`, `ProjectOrchestrator`, `Runtime`, `GitOps`, `TunnelCoordinator`. The new tool bodies need only one extra dep (`SnapshotStore`).

## Architecture decisions

### Decision 1: snapshot = APFS `clonefile` of the host project tree

Primary mechanism on macOS: `clonefile(2)` of `~/.opnble/repos/<project-id>` to `~/.opnble/snapshots/<project-id>/<snapshot-id>/`. Single syscall, byte-for-byte CoW, instant regardless of `node_modules` size.

Fallback on Linux and Windows: recursive `std::fs::copy` of the project tree, gated behind a feature flag and not shipped as a release target for v1.1.

**Rejected: OverlayFS inside the VM.** OverlayFS would solve "capture container-internal state," not "capture the project tree." The thing the agent edits lives on the host, not in the VM. OverlayFS-in-VM is a different feature and would cost a kernel verification week we cannot afford.

**What this captures:**

- Every file under `~/.opnble/repos/<project-id>/`, including `node_modules`, build artifacts, `.next/`, `.git/`.

**What this does NOT capture (called out explicitly in user-facing docs):**

- Running dev-server process state, in-flight HTTP, open file descriptors.
- Container-internal mutations outside the bind mount. Example: `podman exec opnble-proj-... apk add foo` modifies layers inside the container, not the project tree. The next container restart loses them.
- Data directories that live inside the container at non-bind-mounted paths (Postgres `/var/lib/postgresql`, Redis `/data`). For Node-only stacks this is a non-issue; for full-stack stacks the SF doc says "this is a v1.2 problem, run your DB on the host."

### Decision 2: `exec_command` runs inside the project container

Implementation path: `agent_client::exec_host(format!("podman exec {container_name} sh -c {escaped_cmd}"))`. The container already has the right Node version, the right `cwd` (`/app`), the right env, and the right port mappings. The dev server sees the same world.

`cwd` is interpreted relative to `/app`; absolute paths within the container are allowed. `env` is merged on top of the container's env via `podman exec --env KEY=VAL`. `timeout_ms` defaults to 60s, capped at 300s for v1.1 (matches the MCP server-side ceiling).

Output policy: buffer and truncate. Stream is v1.2. Combined stdout + stderr capped at 256 KiB. The cap is encoded server-side; clients see a `truncated: true` flag and the tail of the buffer. Reasoning: agents that follow up with another tool call (`tail_logs`) tolerate this well; streaming forces a much larger protocol surface (rmcp progress notifications) that is not worth the risk before SF.

### Decision 3: `read_file` and `write_file` go through the host filesystem

Same virtio-fs reasoning: host and VM see identical bytes for any path under the project tree. The MCP tool body resolves `slug -> Project`, joins `project.repo_path()` with the requested path, validates the join stays within `repo_path` (canonicalize, reject traversal), then uses `tokio::fs::{read,write}`. No proto change, no agent re-deploy.

Caps: `read_file` returns at most 1 MiB by default; if `size > max_bytes`, return the first `max_bytes` and `truncated: true`. `write_file` rejects content over 4 MiB to bound RPC payloads. Binary content is allowed; the response carries `encoding: "utf-8" | "base64"` so the agent knows how to interpret it.

Path validation helper lives in `src/tauri/src/mcp/path.rs`, modeled on `agent/src/service.rs:124-148`. Symlinks are followed during canonicalize; if the resolved path escapes the project root, the tool returns a typed `PATH_ESCAPES_PROJECT` error.

### Decision 4: a fork is a new first-class project with `parent_project_id`

A `fork_project` call:

1. Resolves parent project from slug.
2. Allocates a new `ProjectId` and a new port.
3. Computes a child slug: `<parent_slug>-<short_id>` where `short_id` is the last 6 characters of the new `ProjectId` (collision-free by construction since IDs are timestamped).
4. APFS-clones the parent's `repo_path()` to the child's `repo_path()`.
5. Writes a fresh `.opnble` marker inside the cloned tree with the child slug.
6. Inserts the child into `state.json` with `parent_project_id = Some(parent.id)` and `forked_at = Some(now)`.
7. Calls `orchestrator.start_project(...)` with the new id and port. Returns once the new container is Ready.

Discard a fork = the existing project delete flow, which already handles container removal, port release, and disk cleanup.

UI implication: forked projects render as children under the parent in the sidebar, with a small "Fork" badge and the snapshot-id or label they were forked at.

## Data model changes

### `Project` (additive only)

```rust
// src/tauri/src/projects/types.rs
#[derive(Clone, Debug, Deserialize, Serialize, specta::Type)]
#[serde(rename_all = "camelCase")]
pub struct Project {
    // ...existing fields unchanged...

    /// Parent project this one was forked from. None for top-level projects.
    #[serde(default)]
    pub parent_project_id: Option<ProjectId>,

    /// Wall-clock millis when this project was forked. None for top-level.
    #[serde(default)]
    pub forked_at: Option<u64>,
}
```

Both fields default to `None` so existing `state.json` files deserialize unchanged.

### `SnapshotRecord` (new)

```rust
// src/tauri/src/snapshots/types.rs
#[derive(Clone, Debug, Deserialize, Serialize, specta::Type)]
#[serde(rename_all = "camelCase")]
pub struct SnapshotRecord {
    pub id: SnapshotId,             // "snap-{unix_millis}-{rand4}"
    pub project_id: ProjectId,
    pub label: Option<String>,      // optional user-provided tag
    pub taken_at: u64,              // unix millis
    pub size_bytes: u64,             // best-effort, from clonefile post-stat
}

#[derive(Clone, Debug, Eq, Hash, PartialEq, specta::Type)]
#[specta(transparent)]
pub struct SnapshotId(String);
```

`SnapshotId::new` follows the same validation rule as `ProjectId` (alphanumeric + dash).

### `~/.opnble/state.json` schema bump

Snapshots live in their own top-level array so the existing project schema stays untouched:

```json
{
  "projects": [...],
  "next_port": 3001,
  "snapshots": [
    {
      "id": "snap-1747500000000-a3f9",
      "projectId": "proj-1747400000000",
      "label": "before-refactor",
      "takenAt": 1747500000000,
      "sizeBytes": 12345678
    }
  ]
}
```

Snapshot directory layout: `~/.opnble/snapshots/<project-id>/<snapshot-id>/`. The full project tree is cloned in.

### Pruning policy

Cap: 20 snapshots per project, FIFO eviction by `taken_at`. UI exposes "delete snapshot" too. Eviction triggers on every `snapshot_project` call after the new snapshot lands; this keeps the policy in one place and avoids a background sweep. Forked projects do not inherit parent snapshots; they get their own snapshot history starting from the fork point.

## Tool surface (detailed)

All six tools take `slug: string` and resolve through `ProjectStore::get_by_slug` (already implemented in v1). All annotations match v1 conventions: read-only tools mark `read_only_hint`; everything else marks `destructive_hint`. All tools auth through the existing bearer-token middleware. No new auth surface, no new ports.

### `exec_command`

```rust
#[derive(Deserialize, schemars::JsonSchema)]
pub struct ExecCommandArgs {
    pub slug: String,
    pub cmd: String,
    #[serde(default)] pub cwd: Option<String>,      // relative to /app
    #[serde(default)] pub env: HashMap<String, String>,
    #[serde(default = "default_exec_timeout_ms")]
    pub timeout_ms: u64,                            // capped at 300_000
}

#[derive(Serialize, schemars::JsonSchema)]
pub struct ExecCommandOutput {
    pub stdout: String,
    pub stderr: String,
    pub exit_code: i32,
    pub truncated: bool,
    pub duration_ms: u64,
}
```

Flow:

1. Resolve slug to project; require `project.status` to be `Ready` (else return `code: "PROJECT_NOT_RUNNING"` with hint to call `start_project`).
2. Build the wrapped command: `timeout {timeout_secs}s podman exec {env_args} -w {cwd_in_container} {container_name} sh -c {shell_quote(cmd)}`.
3. Call `agent_client.exec_host(wrapped)`.
4. Truncate stdout and stderr each at 128 KiB; set `truncated` if either capped.
5. Return.

Error codes: `PROJECT_NOT_RUNNING`, `EXEC_TIMEOUT` (when `timeout` returns 124), `EXEC_FAILED` (any other non-zero, surfaced through `exit_code` not as an error so the agent can read stderr).

### `read_file`

```rust
#[derive(Deserialize, schemars::JsonSchema)]
pub struct ReadFileArgs {
    pub slug: String,
    pub path: String,
    #[serde(default = "default_read_max_bytes")]
    pub max_bytes: u64,                              // capped at 4_194_304 (4 MiB)
}

#[derive(Serialize, schemars::JsonSchema)]
pub struct ReadFileOutput {
    pub content: String,                            // base64 if encoding == "base64"
    pub encoding: String,                            // "utf-8" | "base64"
    pub size: u64,                                   // unmodified file size
    pub truncated: bool,
}
```

Flow:

1. Resolve slug, compute `abs = canonicalize(project.repo_path().join(path))`.
2. Reject if `!abs.starts_with(canonicalize(project.repo_path()))`. Return `PATH_ESCAPES_PROJECT`.
3. Read up to `max_bytes` via `tokio::fs::File::take(max_bytes)`.
4. Try UTF-8. If valid, return as `utf-8`; else base64-encode and return as `base64`.

Cap default: 1 MiB. Cap ceiling: 4 MiB.

### `write_file`

```rust
#[derive(Deserialize, schemars::JsonSchema)]
pub struct WriteFileArgs {
    pub slug: String,
    pub path: String,
    pub content: String,                            // utf-8 by default
    #[serde(default)] pub encoding: Option<String>, // "base64" to write binary
    #[serde(default)] pub mode: Option<u32>,        // POSIX mode bits
    #[serde(default = "default_true")]
    pub create_parents: bool,
}

#[derive(Serialize, schemars::JsonSchema)]
pub struct WriteFileOutput {
    pub bytes_written: u64,
}
```

Flow: validate path same way as `read_file`, decode content per encoding, `tokio::fs::create_dir_all` parent if requested, `tokio::fs::write` atomically (write to `<path>.tmp`, then rename). Reject content over 4 MiB.

### `snapshot_project`

```rust
#[derive(Deserialize, schemars::JsonSchema)]
pub struct SnapshotArgs {
    pub slug: String,
    #[serde(default)] pub label: Option<String>,
}

#[derive(Serialize, schemars::JsonSchema)]
pub struct SnapshotOutput {
    pub snapshot_id: String,
    pub label: Option<String>,
    pub taken_at: u64,
}
```

Flow:

1. Resolve slug.
2. Generate `SnapshotId` via `format!("snap-{}-{}", unix_millis, hex(rand4))`.
3. Compute destination: `paths::snapshots_dir().join(project.id.as_str()).join(snapshot_id.as_str())`.
4. Call `vm::clone::clone_tree_or_copy(&project.repo_path(), &dest)`.
5. Insert `SnapshotRecord` into store; trigger FIFO eviction if count > 20.
6. Return.

The dev server keeps running. Snapshot does NOT pause anything. Files captured are the bytes-on-disk at clonefile time; if a `node_modules` write was in flight, we capture either pre- or post-write per file, but the directory is consistent at the byte level (clonefile is atomic per inode).

### `fork_project`

```rust
#[derive(Deserialize, schemars::JsonSchema)]
pub struct ForkArgs {
    pub slug: String,
    #[serde(default = "default_fork_count")]
    pub count: u32,                                  // 1..=4, capped
    #[serde(default)] pub label: Option<String>,
}

#[derive(Serialize, schemars::JsonSchema)]
pub struct ForkChild {
    pub slug: String,
    pub parent_slug: String,
    pub status: String,
    pub port: Option<u16>,
    pub url: Option<String>,
}
```

Returns `Vec<ForkChild>` of size `count`. Each child is created sequentially; parallelize only if `count == 1` produces issues (it should not). Children are returned once each is `Ready` (block until status flips, reusing v1's `wait::wait_for_status`).

Per-child flow:

1. Allocate new `ProjectId` and new port.
2. Compute child slug: `<parent_slug>-<short_id>` where `short_id = project_id.as_str().chars().rev().take(6).collect()`. Collision impossible by construction (id is unique by timestamp).
3. Compute child `repo_path` under `paths::repos_dir().join(new_id)`.
4. `vm::clone::clone_tree_or_copy(parent.repo_path(), &child_repo_path)`.
5. Rewrite `.opnble` in the child tree with the new slug.
6. Optionally append `.cursor/mcp.json` (re-run `mcp::install::write_project_mcp_config`).
7. Build `Project` with `parent_project_id = Some(parent.id)`, `forked_at = Some(now)`, `installed = parent.installed`. Insert into store.
8. `orchestrator.start_project(app, new_id, port)`; await Ready or timeout.
9. Return child summary.

Port allocator: `next_port` is monotonic; N siblings get N sequential ports cleanly. No change needed.

### `rollback_project`

```rust
#[derive(Deserialize, schemars::JsonSchema)]
pub struct RollbackArgs {
    pub slug: String,
    pub snapshot_id: String,
}

#[derive(Serialize, schemars::JsonSchema)]
pub struct RollbackOutput {
    pub snapshot_id: String,
    pub restored_at: u64,
    pub interruption_ms: u64,                       // time the dev server was down
}
```

Flow:

1. Resolve slug, load snapshot record, verify `snapshot.project_id == project.id`.
2. `orchestrator.force_stop_and_remove(&project.id)` (reusing v1).
3. `std::fs::remove_dir_all(&project.repo_path())` + `vm::clone::clone_tree_or_copy(&snapshot_path, &project.repo_path())`.
4. `orchestrator.start_project(app, project.id, port)` and await Ready.
5. Return.

Interruption window: typically 5 to 15 seconds (container teardown plus container restart). This is documented; the agent and the user should expect a brief gap.

## Test strategy

- **Unit tests** for every new module (snapshot store, clone_tree, path validation, tool bodies). The bar is "matches v1 coverage density" (v1 added ~330 lib tests).
- **Integration tests** in `src/tauri/tests/mcp_v1_1.rs`:
  - Snapshot then rollback restores file content.
  - Fork creates a child that reaches Ready and serves on a different port.
  - `exec_command` against a running container returns expected stdout/exit.
  - `read_file` rejects `../` traversal.
- **Manual smoke** at each phase gate; explicit smoke list in PR descriptions.
- **End-to-end** through Cursor and Claude Code in J1.

We do not write tests against mocked agent/runtime behavior for the agent loop itself; the integration tests use real podman in CI (matches v1's approach).

## Known unknowns and resolving experiments

1. **APFS `clonefile` of a directory containing a 2 GiB `node_modules` actually completes in <1s.** Verify on day one with a one-off binary that calls `clonefile` and times it. If false, snapshot UX falls apart and we redesign.
2. **`podman exec` inside the Alpine VM honors the `timeout` binary correctly.** Verify with a `sleep 9999` test. `timeout` is part of coreutils on Alpine; should be present, but verify.
3. **virtio-fs honors writes within a few hundred milliseconds.** Already used in v1 for hot reload; restating that snapshots see the latest bytes. Sanity-check by writing a file and immediately snapshotting; assert the byte is in the snapshot.
4. **Forking while the parent is mid-`npm install`** produces a child with a half-installed `node_modules`. Mitigation: `fork_project` requires `parent.status == Ready`, which already implies install completed.
5. **Rollback timing under a heavy dev server** (e.g., webpack rebuilding). Container stop with `t=10` plus restart should still come in under 15s. If not, we add a "warn user" path in the UI and document the interruption.

Each unknown is resolved by an experiment in the first 3 days; the design holds or we redesign before Vlad starts V3.

## What we will NOT have working by Jun 9 (honest list for SF)

- No container-internal snapshotting. If you `apk add` something inside the running container, it is gone on the next restart. Use the project tree.
- No snapshot of Postgres or Redis data unless those data dirs live under the project tree. Run the DB on the host or wait for v1.2.
- No streaming stdout from `exec_command`. Long-running commands buffer up to 256 KiB and return on exit or timeout. If you want to watch a process live, use `tail_logs`.
- No multi-host or cloud sandboxes. Fork is local-only, bounded by your Mac's CPU and RAM.
- No Python or Go base image; the bundled image is Node-only. Bring-your-own-Dockerfile is v1.2.
- No editor integration beyond `.cursor/mcp.json`. Claude Code, ChatGPT Desktop, and other MCP clients work via the same JSON in their own config locations (doc-only).
- No "undo my last agent action" higher-level abstraction. The agent has to explicitly snapshot before risky changes. v1.2 may auto-snapshot on every Nth tool call.

## Cut-line if we slip

In priority order, things we drop without losing the SF story:

1. `fork count > 1` (drop to `count == 1` always; agents that want multiple forks call the tool multiple times).
2. UI snapshot list per project (replace with a single "rollback to most recent snapshot" button).
3. Ring buffer of recent tool calls in Settings (drop; users see them in Cursor's MCP log).
4. Signed dmg polish (ship unsigned with documented Gatekeeper override; only acceptable if J2 confirms the cohort is tolerant).

We do NOT drop `read_file`/`write_file`/`exec_command`/`snapshot_project`/`rollback_project` even at the cost of UI rough edges. Those five tools are the core value proposition.
